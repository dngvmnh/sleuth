## 2. How you work

For each work package:
1. `git fetch`, then create a branch `<type>/<slug>` from `origin/main`.
2. Do the work. Keep to `.kiro/steering/` and the specs. Use the matching custom agent's rules (frontend-builder, backend-builder, media-builder) for that area.
3. Run `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm test:property`, `pnpm check:contracts`, `pnpm build`, and `node tools/kiro-hooks/hook.mjs ghost-scan`. Fix failures. Run Playwright for UI changes.
4. Tick spec tasks and append a dated entry to `docs/kiro-engineering-journal.md` (what was built, which Kiro features were used, what failed, real test numbers).
5. Commit with Conventional Commits and **no AI co-author trailer**, push, and open a PR with a short description and the owner as reviewer.
6. Wait for CI. If it is green, squash-merge it yourself (`gh pr merge --squash --delete-branch`). If it is red, fix it on the same branch. A CI job that fails for an infrastructure reason (for example the Supabase port being taken) may be re-run once.
7. Move to the next package. Never leave `main` red.

Keep packages small enough to merge within about half a day of work. Split a big package into several PRs rather than one huge one.
